# Stage 3: provenance and reason to exist

The unit is each doc file and each docs folder that stage 2 kept. For every unit, establish five things before proposing a verdict:

1. **Origin**: what created it, and when.
2. **Original purpose**: what it was created for, quoted from the creating tool or session where possible.
3. **Readers today**: what reads it by name, and what reaches it through a pointer.
4. **Still used**: whether each of those readers is still used on this project.
5. **Overlap**: other files that cover the same topic.

## Origin and purpose: the chain of evidence

Walk the chain in this order and record which link established the answer. When two links disagree, report both.

1. **Git history.** Read the creating commit's `history.created.subject` and the whole of `history.created.body`, its author and trailers, and, with `git show --stat`, the other files it added. A squash merge's subject names the merged pull request; the commit that wrote the file is a line of its body. A line naming the file with a command or a skill, or a commit that also adds that tool's configuration, names the creator. An agent trailer (`Co-Authored-By: Claude`, a session link) says an agent session wrote the commit; whether the user asked for the file is a question for the transcripts and link 5.
2. **Transcripts.** The session that wrote the file and the skills invoked in it (`created_in_session`). Open that session's transcript and quote the line that wrote or announced the file.
3. **Installed skills that name the file** (`named_by_tools`, with quoted lines). A skill whose instructions write the file is a creator candidate; its text about the file is the best quote for the original purpose.
4. **A web lookup**, made now: search the file name with the tool or convention it suggests. Cite the URL and the date you read it.
5. **The user.** Ask when the first four links leave the origin open, and in three cases where they look settled:
   - **An agent-made rule or convention.** A file, folder or rule created by an agent session with no request from the user quoted in that session: its origin stays open. Ask "did this come from you?".
   - **A convention whose source is gone.** A convention that comes from a tool no longer installed or no longer invoked (`tools`, `skills_invoked`), or that the user's global files contradict: ask "is this still your method?".
   - **A technical rule an agent wrote.** Build its file first: who wrote it (commit, session, the user's words if any), the risk it covers according to a primary source (the vendor's documentation) or an incident in the project (an issue, a commit), and whether a tool already checks it (a linter, a CI step, the platform's own checks). Give the technical verdict yourself, with those sources; put to the user only what engages them: their own rule, a cost, a choice of method.

Write the origin as a checkable sentence that quotes the line naming the file: "Created on 2026-03-02 in commit `a1b2c3d`, whose message says "onboarding notes generated by `<tool> init`", during a session that invoked the `<skill>` skill."

## Readers and whether they are still used

A file has one of two kinds of reason to exist. No single source states this split; it is drawn from the owners below.

- **A named consumer reads it by name**: a platform, a harness, or a tool or skill. The consumer fixes its location. For a platform or harness, the inventory gives the rule and its vendor URL (`harness[].source`).
- **Someone reaches it through a pointer and uses it.** These files have no fixed location, and an unread one is a candidate for deletion or for being marked obsolete:
  - [Google, *Software Engineering at Google*, ch. 10][swe] [vendor]: "When a document no longer serves any purpose, either remove it or identify it as obsolete";
  - [Anthropic, skill authoring best practices][skills] [vendor]: "If Claude never accesses a bundled file, it might be unnecessary or poorly signaled".

The reader to establish is use of the content: a session that opens a file for what it says. Count two kinds of open apart from use:

- **What the project's own instruction makes agents do.** When an instruction of the project makes agents list a folder or write into it (a pointer in an always-loaded file, a rule to write one doc per issue), the sessions' reads and writes show that the instruction is followed, not that the content is used.
- **A doc copied as a template.** A dated doc that sessions open to copy its form (the latest record of a series, read before writing the next one) spreads the practice of its date: it is a risk, not a reader. Count those opens apart.

For each reader, state whether it is still used, from the inventory:

- a tool that names the file: how often it was invoked in this project, and when last (`tools[<id>].invocations`, `last_invoked`), and how many of those invocations a subagent made (`in_subagents`). Report the split: a tool invoked only by subagents was never invoked from a main session in the window;
- a harness: its loading rule (`harness`, with `condition_met`) and the sessions that loaded the file (`loaded_in_sessions`), or, for a harness whose logs were not read, the user's answer from stage 1;
- a pointer: how many doc files point to it (`pointed_to_by`), and whether sessions opened the file (`sessions.read`, `last_read`);
- Cursor: the conversations that mention the file (`cursor_conversations`), when its logs were found.

A file marked `orphan` has none of these. It is a candidate for deletion, still subject to the user's answers about unread logs and to the tools that name its folder (`folders[].named_by_tools`): when a tool's quoted line shows it reads or writes the files there (an ADR folder its skill writes to), that tool is a reader of the file; when it names the folder for its own purpose (a spec "under `docs/`"), it is not.

Say what the evidence covers. Reads and loads are counted under the path the file had at the time: for a renamed file, add the counts of its former paths (`history.former_paths`). A skill with no invocation in the transcripts is "not invoked between <first date> and <last date>" (`limits.transcripts`). Ask the user whether a reader the logs cannot see is in use.

Before proposing a rename or a move, list the consumers of the current name and location **and** of the new ones: each has its own readers. For a file already renamed (`history.former_paths`), the tools that still name its old name (`named_by_tools` with `via: former_path`) lost it at the rename: report them, with their quoted line.

## Verdicts

A doc that is a symbolic link to a file that stays (`symlink_to`) costs nothing of its own: it carries no words and no passage. Report it as a link to its target, with the harnesses that read it under its name; it stays as long as its target does.

Propose one per unit, with its source:

| Verdict | When | Source |
|---|---|---|
| Keep | A reader uses it, and its content belongs there (stage 5 judges the content) | the reader found above |
| Merge into X | Several docs cover one topic | [*SWE at Google* ch. 10][swe] [vendor]: "designate canonical documentation … consolidate other associated documents into that primary source (or deprecate the duplicates)" |
| Move | Its consumer reads it at another location; or it holds a procedure or one area's rule | the consumer's rule (`harness[].source`, or the tool's quoted line); [Anthropic memory page][memory] [vendor]: "If an entry is a multi-step procedure or only matters for one part of the codebase, move it to a skill or a path-scoped rule instead." |
| Archive | A plan or design doc whose code is built: it stays as a dated record and stops being updated | [Google docguide][docguide] [vendor]: "once the code is implemented, design docs should serve as archives of these decisions, not as half-correct docs" |
| Mark obsolete | No longer serves a purpose, but readers still land on it: say so at its top and point to what replaced it | [*SWE at Google* ch. 10][swe] [vendor]: "identify it as obsolete (and, if available, indicate where to go for new information)" |
| Supersede | A reversed decision record: a new record replaces it, the old one stays and says so | [Nygard][nygard] [practitioner]: "keep the old one around, but mark it as superseded" |
| Convert to automation | It is a deterministic list of steps | [Google SRE workbook][sre] [vendor]: "If your playbooks are a deterministic list of commands … we recommend implementing automation." |
| Delete | It is certainly wrong, or serves no purpose: no reader, nothing points to it | [Google docguide][docguide] [vendor]: "First delete what you're certain is wrong, ignore what's unclear."; [*SWE at Google* ch. 10][swe], quoted above |

Root or `docs/`: no source was found that gives a rule for where a file no consumer reads by name should sit, nor how many files a repository root should hold. A move made for tidiness is the user's choice; say that no source decides it.

## Docs folders

A folder is a unit of its own. Establish what started the convention (the first commit adding a file there, or the skill or template that writes there), what reads the folder by path (`folders[].named_by_tools`), and whether its files share one purpose ([*SWE at Google* ch. 10][swe] [vendor]: "A document should have, in general, a singular purpose, and stick to it."). The verdict covers the folder; files that depart from it get their own.
